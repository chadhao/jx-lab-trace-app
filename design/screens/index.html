规则

自动化优先：每页必填项 ≤ 1

这是本 App 的设计总纲，优先于「美观」与「信息丰富」。判断一个页面合格与否，只问一句：工人在这页上必须亲手输入几个字段？0 个最好，1 个可以接受，2 个以上必须回去改流程。

七条落地规则

  • ① 扫一次，能带的全带出。码里已有对象类型、日期、物料、车序、袋序/批序，解析后直接填好，不再让工人选下拉。
  • ② 上一步就是下一步的默认值。本袋重量继承袋记录、设备继承本批、班组继承登录人所属班组——默认值要可见、可改，但不必手输。
  • ③ 序号自动分配。袋序、批序、成品批序、样品编号由系统取下一个可用值，界面只显示、不提供编辑。要改＝作废重来，避免人为跳号造成谱系空洞。
  • ④ 判定自动做。录值即与标准值比对，结论默认「合格」并高亮，异常时才点「不合格」——把常见路径做成零动作。
  • ⑤ 能接设备就不手输。磅秤/天平若能以蓝牙或 HID 键盘方式输出，优先直读；不能接时用大数字键盘，且同一袋重量只需录一次。
  • ⑥ 一次点击做完一件事。提交按钮只有一处，不做「保存草稿 + 提交」双按钮；草稿＝系统自动留的，不是人点的。
  • ⑦ 每页只回答一个问题。一个页面塞两个任务，就要工人做两次判断——拆开比堆着快。

S01

登录 · 飞书授权

工人只有一次机会对登录页建立信任：一眼知道这是公司的系统、点一个按钮就能进。因此这一屏不放表单、不放账号密码、不放选择角色的下拉框——所有身份信息由飞书账号决定。

设计要点

  • 一个主按钮。全屏只有一个可点的实心按钮，其余都是文字说明——避免误触，也避免工人犹豫。
  • 失败必须可辨因。不写「登录失败，请重试」这种废话；直接说清是网络、授权被拒、还是账号没分角色，三种给三种出路。
  • 不显示账号密码任何痕迹。WebView 授权页由飞书渲染，APP 只负责打开与回收 Cookie。
  • 底部露出服务端状态。车间现场排查「是不是没网/没连上服务器」时，工人自己就能看。

实现约束

  • WebView 打开 /api/auth/feishu/start，授权完成回落到站内页后，读取 CookieManager 的 jx_sid 注入 OkHttp 的 CookieJar。
  • 会话 12h 滑动续期；过期时不跳回登录页，而是弹「会话已过期，请重新验证」并在原位重新授权，避免现场作业中断。
  • 登录成功后调 GET /api/me 取姓名、角色、权限点，缓存在本地用于首页渲染。

S02

现场首页（收货员为例）

首页要同时回答三个问题，按重要性从上到下排：① 有没有做了一半的活（进行中）；② 今天剩多少（待办数）；③ 去哪做（四个入口）。只有「进行中」为空时才让位给「今日待收总数」。

四条硬规则

  • 进行中永远置顶。做了一半的作业比新作业优先——现场最常见的事故是「贴到第 12 袋被打断，回来忘了从哪继续」。
  • 色块只放一个数字。角标＝待办数；不放百分比、不放两个指标，避免工人站着一秒内读不出来。
  • 色块不因断网变灰。扫码取景不耗流量，断网时仍可扫；灰掉会让工人以为坏了。
  • 底部扫码键常驻。任何页面伸手就能扫，不需要先回首页。

角色自适应

  • receiver：收货 / 建袋打码 / 装车出场 / 追溯（如本页）
  • production：建批 / 投料 / 取样 / 成品打码
  • 质检员：不装 APP——检测、留样入库、留样借还全在化验室电脑；取样由生产班组做
  • management / sales：报表 / 追溯 / 批次档案 / 我的，全部只读
